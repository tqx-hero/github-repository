### Redis：

### 1、数据结构

#### 	A、String：

​	底层数据结构是自己封装的由C语言的字节数组（char[]）为中心构建的一个SDS结构体，类似java的List。

###### 	注意：这里的char[]不是Java的字符数组，是C语言的字节数组，因为C没有byte数组，用char[]来存储字节。

​	数据结构如下：

```java
class SDS{
    int len;  //长度
    int alloc; //数组总容量
    char[] buf; //字节数组
}
```

##### 	为什么不用C里面的字节数组，反而自定义了一个结构体？

###### 	 因为C中想获取数据的长度，需要进行遍历数组，时间复杂度为O(n),这里用len来表示数组长度，获取长度不需要再遍历，时间复杂度变为O(1)，典型的以空间换时间的做法，提升查询效率。



###### 	细讲C语言中的字节数组缺点：

##### 	1、C中字符串靠\0来判断结束，遇到"\0"直接被截断，二进制不安全。

##### 	2、没有长度字段表示，所以如果查询长度需要遍历数组，时间复杂度O(n)相对较高。java里的byte数组是封装过的，长度与Redis同样是一个字段。

##### 	3、是一块裸奔的内存区域，数组长度无约束，只能靠程序逻辑划界，使用不当极易产生内存越界，轻则数据篡改，严重导致系统崩溃。

##### 	4、扩容极其麻烦，需要手动分配内存malloc，拷贝旧数据、释放旧内存、更新指针，一不注意就内存泄漏。



##### 	由于在Redis中String类型底层是字节数组，所以Redis的String类型可以存储各种由字节流形成的数据，包括字符串、文件、视频、图片、数字、JSON等。

###### 	Redis中String的扩容规则：

###### 		1、used/size >=1时触发（或>=5强制触发，防止链表过长），创建新数组，容量翻倍（4-->8）；

###### 		2、逐步迁移桶到新哈希表，不是一次全部迁移，而是在每次crud时只搬一个桶（因为单机下redis是单线程，全量迁移会导致业务执行阻塞）。

###### 		3、增：直接hash加入新表；删改查：先查旧表，查到了操作，没查到在新表查然后操作。

##### 		至于为什么没用红黑树代替桶内的单向链表：

###### 			1、redis在定义数据结构时只规定了next指针，没有prev，再次修改会导致兼容性问题。

###### 			2、redis是单线程模型，红黑树在扩容时迁移需要全量一次性完成，否则再去遍历、转换颜色、旋转等会非常复杂，单线程下会导致业务执行效率低下，redis失去优势。

###### 			3、HashMap使用场景决定了数据会频繁进行批量或全部的遍历，需要急需返回数据，红黑树结构是为了避免尽早扩容带来的全量迁移性能损耗，而redis作为DB，首先基本不会遍历所有key的操作，而且可以不用这么着急的一次性全量迁移，所以采用了渐进式的rehash迁移方式，让迁移分摊到每一次的业务操作中，让用户无感知。同时也解决了链表过长的问题。

#### 	关于惰性释放有两种：

#### 		1、惰性过期：

###### 			当用户访问时才会触发。用户进行对key读写时，先检查该key有没有设置过期，设置过期并且已经超时的直接清除。

​			优点：不额外占用线程去进行扫描，CPU能更多的进行业务上的操作。

​			缺点：占内存，有些过期的大key一直释放不掉。

#### 		2、异步释放：

​			设置定时时间，比如每10秒异步线程进行一次检查，或者主动flushall、flushdb时即时删除冷数据。

​			配置项：

​			

```java
# 内存淘汰时是否异步释放
lazyfree-lazy-eviction yes
# 过期删除时是否异步释放
lazyfree-lazy-expire yes
# 主动 DEL 时是否异步释放
lazyfree-lazy-server-del yes
# slave 接收主库 DEL 时是否异步
replica-lazy-flush yes
# 用户执行 FLUSHDB/FLUSHALL 是否默认异步（6.2+）
lazyfree-lazy-user-flush yes
```

​			执行过程是：

​				异步线程在如上配置时，当达到某个条件，如主动del或flushall时，主线程会执行删除key操作。

​				主程序会查找超时的key，去除key的引用，俗称摘链，相当于java的赋值null。

​				赋值后，判断key的大小（基本就是数据的长度），如果数据不大就顺手释放清除，如果过大，摘链后交给异步线程（相当于垃圾收集器）慢慢			清理掉。

​			优点：能及时回收更多的内存空间，省内存。

​			缺点：后端异步线程的清理过程会占用CPU资源。



##### 	Redis的三层删除机制：

###### 		1、惰性删除：以上情况就是这样，查询时才会进行检查数据是否过期，然后根据key大小直接删除或者异步删除。

###### 		2、定期删除：每秒定期从db中随机抽取带有时间的key检查是否过期，过期直接删除，同时检查清除已占用的时间有没有超过CPU的占用率（25%），如果清理时间过长，就会立刻停止，清理不完的等下次再抽取清理。

​			这种方式很像G1收集器，以一个时间为基准，在这段时间内回收一部分垃圾，剩余的没清理完等下次，优点是不会占用CPU太长时间而导致业务方面的卡顿。但是不能彻底清除垃圾，极端情况一直没抽到过期大key的话，空间会一直不能释放。

###### 		3、内存淘汰：类似full gc。写数据时发现内存占用量超过设定的最大redis存放数据的内存（类似jvm的堆内存）时触发。

#### 			注意：内存淘汰判断只有在写数据，当分配内存失败时进行判断已用内存是否达到上限，读删操作不会判断。

###### 		有8种淘汰策略，其中1种不处理，写抛异常、读删正常。

###### 		4种针对定期key：最近使用少的、使用频率少的、随机、快要过期的。

###### 		3种针对所有key：

##### 			lru：删除最近没使用的key；

##### 			lfu：删除使用频率少的key；

##### 			random：随机。

###### 		生产环境大多使用lru，或者lfu，不考虑定期key，因为到达内存淘汰这个程度说明内存已经很紧张了，必须针对所有的冷数据处理，而且前面的两层删除机制（惰性删除和定期删除）已经针对定期key做处理了，到这一步问题最大的就是非定期的冷key。

##### 	虽然内存淘汰的机制很像JVM的full gc，但是效率比full gc高很多，因为内存淘汰不是STW，集中gc老年代，而是随机抽取少量副本，根据设定的淘汰策略选定清除的key，然后通过异步BIO线程进行gc，样本少、cpu占用率低，最大程度保证了业务执行的流畅度。

> [!IMPORTANT]
>
> ##### 生产环境的maxmemory必须配置，同时必须指定内存淘汰策略（lru或lfu），设定删除key操作由异步线程执行。

​		

```java
maxmemory 6g    #大小由机器决定，建议设定为机器的70%-80%
maxmemory-samples=5  # 淘汰策略触发时采样数，默认值为5
maxmemory-policy allkeys-lru  # 淘汰策略，建议使用lru或lfu
lazyfree-lazy-eviction yes    # 内存淘汰用异步删除
lazyfree-lazy-expire yes      # 过期删除用异步
lazyfree-lazy-server-del yes  # DEL 命令用异步
lazyfree-lazy-user-del yes    # UNLINK 本来就是异步
```



整个运行是这样的：

###### 		1、写数据发现内存不够触发淘汰策略、执行del、flush等命令删除过期key、get/set  key时主线程发现key已过期。

###### 		2、触发主线程的删除key的函数

###### 		3、主线程对这些key进行摘链，切断key的所有引用（类似java中将对象的所有引用置为null）。

###### 		4、判断key的长度大小，超过一定阈值交给异步线程回收，小的立即回收。

###### 		5、当主线程处理key超过一定时间（一般是25%的内存占用率），立即停止key的回收，交给异步线程清理。



#### LRU与LFU：

​	两者的数据结构一致，表示的字段相同，但是字段内容不一致。都是一个24b的数据。

```c
typedef struct redisObject {
    unsigned type:4;
    unsigned encoding:4;
    unsigned lru:24;  // 🔥 核心：LRU 或 LFU 都存在这里
    int refcount;
    void *ptr;
} robj;
```



##### 	LRU：存储的是时间戳，即用户更新key的最近时间。

##### 	LFU：存储的前16b是用户最近访问的时间，后8b是用户的访问次数，次数支持时间衰减（可配置）。

​	在内存淘汰不同策略下这个字段存储的数据不相同。

```c
if (server.maxmemory_policy & MAXMEMORY_FLAG_LRU) {
    // 按 LRU 逻辑：比较 lru 时间戳
} else if (server.maxmemory_policy & MAXMEMORY_FLAG_LFU) {
    // 按 LFU 逻辑：先比较频率，再比较时间
}
```

两种均可，只是侧重点不同：

​	LRU：由于只存储的是时间戳，淘汰阶段比较大小，小的命中，所以会选择长时间没访问的key，不关注频率，换句话说，对热数据不友好。

​	LFU：粒度更细，而且支持配置时间频率缩减的效果，使得在筛选阶段不容易命中热点用户，用于注重保留热点数据的场景。但是由于需要轮询修改字段的后8b数据，所以性能上来说比LRU稍慢。
